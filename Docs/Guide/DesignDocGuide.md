# 设计文档撰写指南

> **性质**：写作参考指南（**不是**强制规范；与 `Docs/DevSpec/` 下的规范冲突时以规范为准）。
> **来源**：对 `E:\GitRepo\GitHub\ACANX\AHA\Docs\Design` 22 篇设计文档的体例统计与归纳（2026-10-29 采集，数据见附录 B）。
> **用途**：撰写 `Docs/Design/` 下设计文档时对照参考，也可作为评审时的检查依据。

---

## 1. 文件放在哪、怎么命名

- 设计文档建议放在 `Docs/Design/`；过程文档（带 `yyMM-NNN-` 编号的落地清单）仍放 `Docs/Refactor/`。
- 文件名建议用 **`<主题>Design.md`**，主题为英文大驼峰（AHA 22 篇里 19 篇如此）：

  | 写法 | 例子 | 说明 |
  |---|---|---|
  | 推荐 | `CdeuWorkflowDesign.md`、`DesktopAutoUpdateDesign.md` | 一个主题一篇，主题名即文件名 |
  | 可接受 | `ArchitectureOverview.md` | 跨子系统总览类，用 `…Overview.md` |
  | 可接受 | `InternalProtocolSpec.md` | 偏契约/协议约束的，用 `…Spec.md`，但注意别和 `Docs/DevSpec/` 的规范混淆 |
  | 不建议 | `cdeu-design.md`、`CDEU设计.md`、`Design_Cdeu.md` | 小写/中文/下划线混排，检索和排序都别扭 |

- 一主题一篇。AHA 实测中位 **271 行**、最长 940 行；如果一篇要写到 900 行以上，通常说明该按「总体设计 + 分模块设计」拆开（`DesktopDesign` 与 `DesktopNativeDesign` 就是这种拆法）。

## 2. 一份设计文档通常长什么样

AHA 的通用骨架（括号内为实测覆盖率）：

```markdown
# 中文标题（如「日志设计」，不带文件名、不带版本号）

**文档版本**：v1.0.0
**状态**：草案 / 生效 / 冻结
**生效日期**：YYYY-MM-DD
**最后更新**：YYYY-MM-DD
**负责人**：@ACANX
**适用版本**：<产品> <版本>
（以上 6 行：16–17 / 22 篇）

---

## 变更日志
| 版本 | 日期 | 变更内容 | 变更人 |
（19 / 22 篇；且全部是这 4 列）

---

## 0. 定位与读者
（9 / 22 篇用了 0 号章；说明本文讲什么、谁该读、配套文档在哪）

## 1. 目标与边界
| 目标 | 说明 |
（6 / 22 篇显式写了「不在范围内」）

## 2..N 主体章节

## 实现现状 / 已知限制（12 / 22 篇用 ✅ ⛔ ⚠ 标注）

## 相关文档（8 / 22 篇）

## 源码索引（2 / 22 篇，本仓库建议加上）
```

建议保留的三段「低投入高回报」内容：

| 段落 | 为什么值得写 |
|---|---|
| `0. 定位与读者` | 三句话就能让后来者判断「这篇要不要读」，避免在 300 行里找答案 |
| `1. 目标与边界` | 明确「不负责什么」，比罗列功能更能减少误解 |
| 源码索引（文件 → 职责） | 文档与代码之间的桥；读者从结论直接跳到落点 |

## 3. 章节怎么编号、按什么顺序

- 一级标题建议写成 `## N. 中文标题`（数字 + 英文句点 + 空格），从 **0** 开始；子节 `### N.M`。
- AHA 实测一级章节数：中位 **10** 章，最多 14 章。超过 14 章时，先想想是不是该拆文档。
- 常见章节顺序（按子系统性质取舍，顺序不必机械照抄）：

| 序 | 章节 | 回答读者哪个问题 |
|---|---|---|
| 0 | 定位与读者 | 这篇讲什么、我要不要读 |
| 1 | 目标与边界 | 为什么要有它、它不做什么 |
| 2 | 术语与概念模型 | 这些词是什么意思、层级怎么分 |
| 3 | 总体架构 | 全貌长什么样（一张图 + 一张表） |
| 4 | 分模块/分阶段详解 | 每块做什么、输入输出是什么 |
| 5 | 数据与接口契约 | 表结构、字段、文件格式、对外接口 |
| 6 | 运行与运维 | 怎么启动、怎么人工干预、出问题怎么查 |
| 7 | 实现现状与已知限制 | 哪些是真的、哪些还只是设计 |
| 8 | 相关文档 | 还想深入该看哪篇 |
| 9 | 源码索引 | 具体实现在哪 |

## 4. 话怎么说

### 4.1 结论先行

每个小节第一句就给判断，后面才写依据。例如：

- 不推荐：「在经历了多次调整之后，我们逐步发现日志装配存在一些问题，经过排查……」
- 推荐：「装配代码看起来正确、日志却不落盘，也没有任何异常——根因是 `ClassLoader.getResources` 不搜索模块路径。」

### 4.2 术语与代码引用

- 正文用简体中文；类名、函数名、表名（含 `schema.table`）、配置键、状态常量、文件扩展名用反引号包起来。
- 缩写首次出现给全称，如「CDEU（Collect → Dedup → Export → Upload）」。
- 同一概念全篇固定一种叫法（前面叫「主表」，后面就别改叫「源表」）。

### 4.3 解释「为什么」

AHA 有 12/22 篇专门写「为什么…」小节，这是设计文档区别于使用手册的关键。建议：

- 每个不显然的选择，补一句「为什么这样」；
- 被否掉的方案写清「为什么不选它」；
- 踩过的坑写进去，带症状和日期（如「装配看似正确却无效，且无异常」）。

常用小标题：`### 为什么不用 X`、`### 取舍`、`### 代价`、`### ⚠ 坑`。

### 4.4 事实、数字与日期

- 数量、比例、耗时的结论，尽量给可复核的数字和来源（如「621 用例 / 行覆盖 80.8%（2026-10-08 实测）」）。
- 写「现状」前先读代码或查库确认；没确认的标「待验证」，别写成既成事实。

### 4.5 尽量避开的写法

| 尽量避开 | 换成 |
|---|---|
| 营销词：「强大」「优雅」「全面提升」「完美解决」 | 具体能力与边界 |
| 模糊断言：「可能会」「应该差不多」「理论上」 | 明确条件与结果 |
| 大段贴代码（几十行以上） | 关键片段（≤ 20 行）+ 源码索引 |
| 只描述「模块 A 负责 A」 | 写输入、处理、输出、失败后果 |
| 把计划写成现状 | 进「实现现状」表，标 `⛔` 并注明目标版本 |
| 表格里裸写竖线 | 写成 `\|`，或把原始串放进代码块 |

## 5. 表格怎么用

- 枚举关系（阈值、状态、触发方式、配置项、字段清单）优先用表格，不写成散文。AHA 表格行数中位 **69 行**，是主力表达方式。
- 建议「一行一字段、一行一取值」，表头至少两列（「项 / 说明」）。
- 同一张表内保持列数一致；不合并单元格。
- 单元格里的竖线要转义为 `\|`；像 `ts|da|ti`、`HH:MM:SS|HH:MM:SS` 这类原始串，放代码块最省事。
- 表格前后各留一个空行（渲染和格式校验都依赖它）。

## 6. 图与代码块怎么放

- 结构图用 ASCII 画（AHA 有 149 个无语言代码块，基本都是树形/数据流图）：树用 `├─` / `└─`，数据流用 `──►`。好处是纯文本可 diff、可搜索。
- 代码块标语言：`bash`（命令）、`sql`、`json`、`yaml`、`go` / `java`（片段）、`text`（纯文本输出）。ASCII 图可以留空语言，但一篇文档内保持一致。
- 命令块里的路径写仓库相对路径（`internal/...`、`Deploy/...`），方便复制执行。

## 7. 状态怎么标

AHA 有 12/22 篇用符号标注实现状态，比自然语言更易扫读：

| 符号 | 含义 | 备注 |
|---|---|---|
| `✅` | 已实现并验证 | 建议在「实现现状」表和能力清单里用 |
| `⛔` | 未实现 / 已停用 | 补一句目标版本或停用原因 |
| `⚠` | 风险、已作废、已知缺陷 | 补影响与处置建议 |
| `☑` | 验收通过 | AHA 在过程性清单里用；本仓库的 `Docs/Refactor/` 也在用 |

## 8. 链接怎么写

- 用相对路径：同目录 `OtherDesign.md`，跨目录 `../DevSpec/XxxSpec.md`。
- 链接文本用文档名或标题，避免「点这里」。
- 建议设一个「相关文档」小节把配套文档收齐（规范、格式、接口、菜单、过程文档），正文就不必到处埋链接。
- 引用代码位置写「路径 + 职责」，不写行号（行号会漂）。

## 9. 篇幅与拆分

| 篇幅 | 参考判断 |
|---|---|
| < 80 行 | 一般还不足以叫设计文档，考虑并入既有文档的对应章节 |
| 150–400 行 | 单子系统设计文档的常见区间（AHA 中位 271 行） |
| 400–900 行 | 可以，但注意章节别超 14 个、每章都要有明确读者问题 |
| > 900 行 | 建议拆：「总体设计」+「分模块设计」，或按并列形态拆 |

## 10. 怎么维护更新

- 版本号习惯：补章节/补说明 → 次版本 `+0.1`；结构或结论变化、推翻既有决策 → 主版本 `+1`。
- 每次修改：更新元信息里的 `最后更新`；在 `## 变更日志` **追加**一行（不改历史行）；按本仓库 `Docs/DevSpec/DocSpec.md` §4 同步 `Docs/CHANGELOG.md`。
- 结论被推翻时，建议保留旧结论并标 `⚠ 已作废`，写清原因与替代方案——历史事故的追溯价值往往高于文档整洁度。

## 11. 写完后的自检建议

非门禁，逐条过一遍能省不少返工：

- [ ] 文件名是 `…Design.md`，放在 `Docs/Design/`
- [ ] 标题是中文、以「设计」结尾，没有重复文件名
- [ ] 6 行元信息齐全，`最后更新` 与变更日志末行日期一致
- [ ] 变更日志是 4 列表格，历史行没被改写
- [ ] `1. 目标与边界` 里有目标表格和「不在范围内」
- [ ] 一级章节 8–12 个，编号从 0 起连续
- [ ] 枚举信息尽量表格化；不显然的选择都写了「为什么」
- [ ] 所有表格列数一致，单元格竖线已转义或换成代码块
- [ ] 代码块标了语言；ASCII 图对齐正常
- [ ] 「实现现状」用 `✅` / `⛔` 标注，未实现项写了目标版本
- [ ] 「相关文档」链接都能打开
- [ ] 数字类结论带来源与日期
- [ ] UTF-8 无 BOM、LF 换行、无行尾空格

## 12. 常见毛病对照

| 常见写法 | 问题 | 改法 |
|---|---|---|
| 「本系统采用了先进的分层架构，极大提升了可维护性」 | 营销词，读完不知道分了几层 | 「分三层：契约层/内核层/接入层；改接入层不影响内核」 |
| 「导出模块负责导出」「上传模块负责上传」 | 同义反复 | 写输入、处理、输出、失败后果四要素 |
| 3000 字无表格 | 枚举信息埋在散文里，难核对 | 把触发方式、阈值、状态全部表格化 |
| 表格单元格内混用转义与非转义竖线 | 列数不一致，渲染错位 | 统一转义，或把原始串放进代码块 |
| 代码里只有接口，文档写「已支持对象存储」 | 计划当现状 | 移到实现现状表标 `⛔ 二期` |
| 改了设计没动变更日志 | 读者无法判断文档是否最新 | 追加变更日志行 + 更新 `最后更新` |
