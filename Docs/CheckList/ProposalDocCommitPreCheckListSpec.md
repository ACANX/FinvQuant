# 提案设计检查清单（ProposalDocCommitPreCheckListSpec）

> 所属：FinvQuant 交付检查清单 · 存放：`Docs/CheckList/`
> 用法：本清单**只列本类特有项**。通用项（范围授权、编译测试、提交纪律、红线）不重复，
> 按 [`CommitPreCheckListSpec.md`](CommitPreCheckListSpec.md) §4 路由取；合并侧复核见 [`MergeCommitPreCheckListSpec.md`](MergeCommitPreCheckListSpec.md)。
> 适用：**动手之前**要拍板的方案、选型、跨模块治理、影响数据/用户可见行为的改动。
> 存放：`Docs/Proposal/yyyyMM-NNNN-大驼峰Proposal.md`（见 [`Docs/Proposal/README.md`](../Proposal/README.md)）。
> 阶段边界：提案里有"待确认决策点"就放 `Docs/Proposal/`；决策点清零、开始动手 → 迁到 `Docs/Design/` 或 `Docs/Refactor/`。

## 1. 什么时候必须写提案

满足任意一条就写，不满足可跳过（避免形式主义）：

- 要改数据口径、表结构归属、主键/唯一键这类**动一次影响全局**的东西；
- 有两个以上可行方案，取舍需要用户拍板；
- 跨模块/跨环境（本地、容器、远端、上游系统）协同；
- 会改变用户可见行为或对外接口契约。

## 2. 骨架（章节缺一项就不算完成）

| 章节 | 必写内容 |
|------|----------|
| 背景与问题 | 现象、触发条件、影响范围（谁受影响） |
| 现状证据 | 数字与命令输出：行数、差异计数、报错原文；不写"感觉有问题" |
| 目标 | 可验收的目标，一条一句 |
| 非目标 | 明确这次**不解决**的相邻问题，防止范围蔓延 |
| 方案候选 | 至少 2 个（含"什么都不改"这一基线），各自代价与收益 |
| 选型结论 | 选哪个、为什么、被否掉的为什么否 |
| 影响面 | 表 / 接口 / 页面 / 迁移 / 部署 / 外部系统 逐项列出 |
| 风险与回滚 | 最坏情况是什么、怎么退、退的代价 |
| 待确认决策点 | 逐条编号（D1、D2…），每条一句可回答的问题 |
| 验收口径 | 怎么判断做成了：命令 + 期望输出 |

## 3. 清单

| 编号 | 检查项 | 判据 |
|------|--------|------|
| PP1 | 问题可复现或可度量 | 有命令/截图/数据；不接受"应该"、"可能" |
| PP2 | 目标可验收 | 每条目标能对上 §2 的验收口径 |
| PP3 | 非目标写了 | 至少一条明确不做的事 |
| PP4 | 候选方案 ≥ 2 且含基线 | 有"不改"这一选项及其代价 |
| PP5 | 被否方案写了否掉理由 | 不是只留一句"不推荐" |
| PP6 | 影响面逐项列出 | 表/接口/页面/部署四类都过一遍，写"无影响"也要写 |
| PP7 | 风险与回滚可执行 | 回滚动作能被另一个人照着做 |
| PP8 | 决策点编号可回答 | 每条是"选 A 还是 B"，不是"要不要重视" |
| PP9 | 未越权预设结论 | 未获批准前不动代码、不改库、不改受保护文档 |
| PP10 | 命名与存放合规 | `Docs/Proposal/yyyyMM-NNNN-*Proposal.md`，编号本目录内唯一 |

## 4. 通过标准

| 结论 | 条件 |
|------|------|
| 批准 | 决策点全部有答复，验收口径明确，影响面完整 |
| 打回 | 缺证据、缺候选、影响面漏项、决策点无法回答 |
| 待定 | 决策点未答完 —— 保持提案状态，**不进入实现** |
