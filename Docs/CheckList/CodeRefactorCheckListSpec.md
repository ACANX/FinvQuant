# 代码重构检查清单（CodeRefactorCheckListSpec）

> 所属：FinvQuant 交付检查清单 · 存放：`Docs/CheckList/`
> 用法：本清单**只列本类特有项**。通用项（范围授权、编译测试、提交纪律、红线）不重复，
> 按 [`PreCommitCheckListSpec.md`](PreCommitCheckListSpec.md) §4 路由取；合并侧复核见 [`PreMergeCheckListSpec.md`](PreMergeCheckListSpec.md)。
> 适用：不改变外部行为的前提下调整结构（改名、拆包、抽函数、换实现、迁文件）。
> 存放：落地步骤清单 `Docs/Refactor/yyMM-NNN-大驼峰名称.md`（编号在 `Docs/` 下全局唯一，见 [`FileNamingSpec.md`](../DevSpec/FileNamingSpec.md) §4）。

## 1. 原则

1. **行为不变**：重构不夹带需求变更；需求变更单独提交。
2. **先护栏后动手**：没有测试覆盖的地方，先补测试再改结构。
3. **小步提交**：每一步都能编译、能跑、能回滚。
4. **范围冻结**：开工前写清"改哪些文件/包"，过程里发现的新问题记下来另开一单。

## 2. 清单

| 编号 | 检查项 | 判据 |
|------|--------|------|
| RF1 | 有行为不变的证据 | 重构前后同一组测试均通过；无测试的路径先补测试 |
| RF2 | 范围冻结并写明 | 步骤清单第一段列出涉及的文件/包，实际改动不越界 |
| RF3 | 分步可独立提交 | 每步单独 `go build ./...` 通过；任一步回滚不影响前一步 |
| RF4 | 不混入格式化噪音 | 纯格式化/`gofmt` 变更单独一次提交，不夹在大改里 |
| RF5 | 文件移动用 `git mv` | `git status` 显示 `R` 而非 `D`+`A`，历史可追 |
| RF6 | 删除代码前确认无引用 | `grep`/`go build` 双向确认；不留注释掉的死代码 |
| RF7 | 不留两套并行路径 | 新旧并存必须有明确切换点与删除计划，写在步骤清单里 |
| RF8 | 公开接口变更同步调用方 | 一次提交内改完全部调用点；或保留兼容层并注明期限 |
| RF9 | 命名与分层统一 | 命名符合 `DbSchemaSpec`/`FileNamingSpec`；不产生同名不同义的概念 |
| RF10 | 测试覆盖不下降 | 受影响包测试通过；被删测试有等价替代 |
| RF11 | 文档同步 | 受影响的设计文档、接口文档、菜单文档同步；失效结论删除而非留"历史说明" |
| RF12 | 可回滚 | 步骤清单写明回滚动作；涉及数据的重构按 [`PreDbChangeCheckListSpec.md`](PreDbChangeCheckListSpec.md) 走 |
| RF13 | 完成后清理 | 临时脚本、兼容开关、旧路径一次性清掉，或写明保留理由与清理时间 |

## 3. 步骤清单骨架

| 章节 | 内容 |
|------|------|
| 现状 | 现在是什么结构、为什么必须改（触发事件或维护成本） |
| 目标结构 | 改完是什么样，一张目录/模块表即可 |
| 步骤分批 | 每批：改什么、验证命令、预期输出、可回滚点 |
| 风险 | 最可能出问题的地方与观测方式 |
| 验收 | 完成后怎么证明"行为没变"（测试、抽样对比、接口返回一致） |

## 4. 常见问题

| 问题 | 后果 |
|------|------|
| 重构顺手改需求 | 出问题时无法判断是重构引入还是需求引入 |
| 一次提交改 40 个文件 | 无法 bisect，回滚代价极高 |
| 新旧路径长期并存 | 两套口径漂移，后来者不知道用哪个 |
| 没有等价性证据 | 只能靠"我觉得没影响"上线 |
