# 技术方案设计检查清单（PreTechDesignCheckSpec）

> 所属：FinvQuant 交付检查清单 · 存放：`Docs/CheckList/`
> 用法：本清单**只列本类特有项**。通用项（范围授权、编译测试、提交纪律、红线）不重复，
> 按 [`PreCommitCheckSpec.md`](PreCommitCheckSpec.md) §4 路由取；合并侧复核见 [`PreMergeCheckSpec.md`](PreMergeCheckSpec.md)。
> 适用：提案已批准、进入实现前的**技术设计**（接口契约、数据结构、流程、兼容与回滚）。
> 存放：`Docs/Design/<主题>Design.md`（骨架参考 [`Docs/Guide/DesignDocGuide.md`](../Guide/DesignDocGuide.md)）；落地步骤清单放 `Docs/Refactor/yyMM-NNN-*.md`。

## 1. 骨架（必写章节）

| 章节 | 必写内容 |
|------|----------|
| 文档头 | 版本、状态（草案/生效/冻结）、负责人、适用版本 |
| 变更日志 | 版本、日期、变更内容、变更人 |
| 模块与职责 | 改动落在哪些包/层，各自职责，不写"由某处处理"这种含糊话 |
| 接口契约 | 方法、路径、参数（类型/必填/默认）、响应信封、错误码号段 |
| 数据结构 | 新表/新列/索引/约束，或键表口径（字段名、可空、唯一性、时间列前缀） |
| 流程与时序 | 正常路径 + 失败路径，谁重试、幂等边界在哪 |
| 迁移与初始化 | 初始数据走迁移脚本、幂等、单事务、末尾收敛校验 |
| 兼容与切换 | 新旧并存时的判定条件与切换点，切换失败怎么退 |
| 性能与容量 | 数据量级、查询索引、批处理大小、耗时预算 |
| 观测 | 日志字段、计数指标、出错时的排查入口 |
| 测试策略 | 单测用例清单、集成用例、空库/克隆库验证方式 |
| 回滚 | 触发条件、回滚步骤、数据是否需要还原 |

## 2. 清单

| 编号 | 检查项 | 判据 |
|------|--------|------|
| TD1 | 设计能对上已批准提案 | 提案编号写进文档头；目标逐条有落点 |
| TD2 | 接口契约完整 | 参数类型/必填/默认、状态码、错误码齐备，能直接写代码 |
| TD3 | 与 `ApiSpec` / `ErrorCodeSpec` 一致 | 信封字段、号段、异常映射无自创 |
| TD4 | 数据结构变更走迁移 | 不靠手工 SQL；初始数据随迁移发布 |
| TD5 | 字段命名合规 | 时间列 `dt_` 前缀；禁 `-ed` 过去分词；不使用生成列做写入字段 |
| TD6 | 唯一性/幂等口径写明 | 唯一键、`ON CONFLICT` 行为、并发下的期望结果 |
| TD7 | 失败路径写全 | 上游超时、部分失败、重试、脏数据 各写怎么处理 |
| TD8 | 切换与回滚可执行 | 有判定条件与步骤；回滚不需要"再写一个新迁移"才能退 |
| TD9 | 性能有量级依据 | 给出预计行数/次数与耗时预算，不写"性能应该没问题" |
| TD10 | 观测点明确 | 出错时先看哪条日志/哪个计数就能定位 |
| TD11 | 测试策略可执行 | 用例可命名、可断言；空库与真实库两种环境都覆盖 |
| TD12 | 与代码一致 | 实现完成后回填差异；文档状态从"草案"改"生效" |
| TD13 | 落地拆分到 `Docs/Refactor/` | 一主题一篇设计 + 一份带编号的落地清单 |

## 3. 常见问题

| 问题 | 后果 |
|------|------|
| 只写正常路径 | 上线后一遇上游超时就靠人肉救火 |
| 迁移与初始化口头描述 | 换环境就要手工补数据，全新部署起不来 |
| 用绝对阈值做校验 | 数据一变就误判、阻塞服务启动 |
| 设计与实现脱节 | 文档半年后失效，没人再信 |
