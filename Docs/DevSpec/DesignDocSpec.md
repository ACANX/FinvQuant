# 设计文档撰写规范（DesignDocSpec）

> 所属：FinvQuant 开发规范 · 存放：`Docs/DevSpec/`
> 适用范围：`Docs/Design/` 下的设计文档；`Docs/Refactor/` 过程文档按本规范**简化执行**（可省略元信息与变更日志）。
> 文档通用规则（语言、表格、编码、变更日志联动）见 [`DocSpec.md`](DocSpec.md)；本规范只补充**设计文档特有**的体例与写法。
> 体例来源：对齐 `E:\GitRepo\GitHub\ACANX\AHA\Docs\Design` 22 篇设计文档的实测统计（见附录 B），据此提炼。

## 1. 文件放置与命名

- **放置**：设计文档一律放 `Docs/Design/`；不得放在根目录、`Docs/Refactor/`（那是带编号的过程文档）或代码目录内。
- **命名**：`<主题>Design.md`，主题用**英文大驼峰**，不得使用中文、连字符、下划线、日期前缀或编号前缀。
  - 正例：`CdeuWorkflowDesign.md`、`DesktopAutoUpdateDesign.md`、`MenuSystemDesign.md`
  - 反例：`cdeu-design.md`、`CDEU设计.md`、`2610-013-CdeuDesign.md`、`Design_Cdeu.md`
- **两种例外写法**（AHA 22 篇中共 2 篇）：
  - 跨子系统总览用 `<主题>Overview.md`（如 `ArchitectureOverview.md`）；
  - 偏契约/协议约束而非方案论证的用 `<主题>Spec.md`（如 `InternalProtocolSpec.md`）。其余情况一律 `…Design.md`。
- **一主题一篇**：一个子系统/一条链路一篇文档；内容超过约 900 行或涉及两套并列形态时才拆分（AHA 最长 940 行，中位 271 行）。
- 新增设计文档必须在 `Docs/CHANGELOG.md` 登记（见 [`DocSpec.md`](DocSpec.md) §4）；若由需求驱动，同时在 `Docs/RequirementList.md` 追加编号条目。

## 2. 文档骨架（强制顺序）

### 2.1 最小骨架

```markdown
# 中文标题（以「设计」结尾，不带文件名）

**文档版本**：v1.0.0
**状态**：草案 或 生效 或 冻结
**生效日期**：YYYY-MM-DD
**最后更新**：YYYY-MM-DD
**负责人**：@ACANX
**适用版本**：<产品名> <版本号>

---

## 变更日志

| 版本 | 日期 | 变更内容 | 变更人 |
|---|---|---|---|
| v1.0.0 | YYYY-MM-DD | 初始版本：<一句话概括覆盖范围> | @ACANX |

---

## 0. 定位与读者

<本文讲什么、不重复讲什么、相关文档清单>

## 1. 目标与边界

| 目标 | 说明 |
|---|---|
| … | … |

**不在范围内**：…

## 2. <概念模型/术语>

## 3. <总体架构>

## 4. <分模块或分阶段详解>

## 5. <数据/接口契约>

## 6. <运维与人机边界>

## 7. 实现现状与已知限制

## 8. 相关文档

## 9. 源码索引
```

### 2.2 各段说明

| 段 | 是否必需 | 写法要求 |
|---|---|---|
| 标题 | 必需 | 中文、以「设计」结尾；不写文件名、不加版本号（版本在元信息里） |
| 元信息 6 行 | 必需 | 字段名加粗 + 全角冒号；顺序固定；`状态` 只取「草案 / 生效 / 冻结」 |
| `## 变更日志` | 必需 | 4 列表格（版本 / 日期 / 变更内容 / 变更人），只追加不修改历史行 |
| `## 0. 定位与读者` | 推荐 | 三句话内说清：讲什么、谁该读、配套文档在哪 |
| `## 1. 目标与边界` | 必需 | 目标用「目标 / 说明」两列表格；紧跟一段 `**不在范围内**：` |
| 主体章节 | 必需 | 见 §3 推荐序列 |
| 实现现状 | 推荐 | 用 `✅` / `⛔` 标注已实现与未实现（见 §7） |
| 相关文档 | 推荐 | 相对路径链接清单，一行一篇 |
| 源码索引 | 推荐 | 「文件 → 职责」表格，让读者能从文档跳到代码 |

## 3. 章节编号与推荐章节序列

- 一级标题用 `## N. 中文标题`（数字 + 英文句点 + 空格），`N` 从 **0** 开始；子节用 `### N.M 中文标题`。
- **章节数控制在 8–12 个**（AHA 实测：中位 10，最多 14）。超过 14 章说明该拆文档。
- 推荐序列（按子系统性质取舍，顺序不随意调换）：

| 序号 | 章节 | 作用 |
|---|---|---|
| 0 | 定位与读者 | 划定阅读范围，给出文档地图 |
| 1 | 目标与边界 | 说明「为什么要有它」与「它不负责什么」 |
| 2 | 术语与概念模型 | 统一词汇，避免后文歧义 |
| 3 | 总体架构 | 一张图 + 一张表说清全貌 |
| 4 | 分模块/分阶段详解 | 逐项写「输入 → 处理 → 输出 → 解决什么问题」 |
| 5 | 数据与接口契约 | 表结构、字段、文件格式、外部接口 |
| 6 | 运行与运维 | 启停、人工干预、告警、排障 |
| 7 | 实现现状与已知限制 | 明确哪些是设计、哪些已落地 |
| 8 | 相关文档 | 交叉引用 |
| 9 | 源码索引 | 文档到代码的落点 |

## 4. 叙述风格

### 4.1 结论先行

- 每个小节第一句必须是**结论或判断**，后续句子才是依据。禁止先铺垫背景再给结论。
- 能用表格表达的枚举关系，一律用表格，不写成长段落（AHA 实测：表格行数中位 69）。

### 4.2 术语与代码引用

- 正文用简体中文；**专有名词保持原文**：类名、函数名、表名、`schema.table`、配置键、状态常量、文件扩展名——统一用反引号包裹。
- 首次出现的缩写给出中文全称，如「CDEU（Collect → Dedup → Export → Upload）」。
- 同一概念全篇只用一种叫法（选「主表」就一直叫主表，不要中英混用）。

### 4.3 必须解释「为什么」

AHA 有 12/22 篇专门用「为什么…」小节解释设计决策。本仓库同样要求：

- 每个非显然的设计选择，必须有一句「为什么这样做」；被否决的方案要写清「为什么否决」。
- 推荐小标题写法：`### 为什么不用 X`、`### 取舍`、`### 代价`、`### ⚠ 坑`。
- 踩过的坑必须写进文档并标注日期与症状（例：「装配看起来完全正确、日志却不落盘，且无任何异常」）。

### 4.4 事实、实测与日期

- 涉及数量、比例、耗时的结论，必须给出**可复核的数字**，并注明来源与日期（例：「621 用例 / 行覆盖 80.8%（2026-10-08 实测）」）。
- 写「现状」而非「应该」：读代码/查库确认后才能写，未确认的用「待验证」明确标注。

### 4.5 禁止项

| 禁止 | 说明 |
|---|---|
| 营销词与空话 | 「强大」「优雅」「全面提升」「完美解决」等一律删除 |
| 无主语的模糊表述 | 「可能会」「应该差不多」→ 改为明确条件与结果 |
| 大段贴代码 | 只贴关键片段（≤ 20 行）；完整实现交给源码索引 |
| 与代码不一致的描述 | 文档必须可被代码核对；改了代码必须同步改文档 |
| 把计划写成现状 | 未实现的一律进「实现现状」表并标 `⛔` |
| 裸竖线 `\|` | 表格单元格内的竖线必须写成 `\|`，否则破坏表格（见 §5） |

## 5. 表格规范

- 强制：**一行一字段、一行一取值**；表头至少两列（「项 / 说明」）。
- 强制：同一表格内所有行**列数一致**；不写合并单元格、不写多行单元格。
- 单元格内的竖线必须转义为 `\|`；含竖线的原始串（如 `ts|da|ti`、`HH:MM:SS|HH:MM:SS`）优先改为代码块展示，避免转义。
- 状态、比例、阈值、清单类信息**优先用表格**；叙述性推理才用段落。
- 表格前后各留一个空行（Markdown 渲染与规范校验都依赖它）。

## 6. 图与代码块

- **结构图用 ASCII 画**（AHA 149 个无语言代码块即此类），不用图片：树形用 `├─` / `└─`，数据流用 `──►`。
- 代码块必须标注语言：`bash`（命令）、`sql`、`json`、`yaml`、`java` / `go`（片段）、`text`（纯文本输出）。ASCII 图可用空语言（```` ``` ````），但同一文档内保持一致。
- 命令块中的路径用仓库相对路径（`internal/...`、`Deploy/...`），便于直接复制执行。

## 7. 状态标记

| 标记 | 含义 | 用法 |
|---|---|---|
| `✅` | 已实现并验证 | 实现现状表、能力清单 |
| `⛔` | 未实现 / 已停用 | 必须补充目标版本或停用原因 |
| `⚠` | 风险、作废、已知缺陷 | 必须补充影响与处置建议 |
| `☑` | 验收通过（过程文档用） | 仅在 `Docs/Refactor/` 使用 |

AHA 实测 12/22 篇使用这三种符号；本仓库设计文档的「实现现状」章节**必须**使用，不得只写「已支持/未支持」的自然语言。

## 8. 交叉引用

- 链接一律用**相对路径**：同目录 `OtherDesign.md`，`Docs/Design/` 引其它目录用 `../DevSpec/XxxSpec.md`。
- 链接文本用文档名或标题，不用「点这里」「详见」这类空文本。
- `## 相关文档` 一章把所有配套文档收齐（规范、格式、接口、菜单、过程文档），避免正文散落链接。
- 引用代码位置写「路径 + 职责」，不写到行号（行号会漂移）。

## 9. 篇幅与拆分

| 篇幅 | 判断 |
|---|---|
| < 80 行 | 通常不足以称为设计文档，考虑并入既有文档对应章节 |
| 150–400 行 | 单子系统设计文档的常规区间（AHA 中位 271 行） |
| 400–900 行 | 允许，但需确保章节数 ≤ 14、每章有明确读者问题 |
| > 900 行 | 必须拆分：按「总体设计」+「分模块设计」拆，或按并列形态拆（如 `DesktopDesign` 与 `DesktopNativeDesign`） |

## 10. 变更维护

- 版本号语义：新增章节或补充说明 → 次版本 `+0.1`；结构调整、结论变更、推翻既有决策 → 主版本 `+1`。
- 每次修改必须：更新元信息里的 `最后更新`；在 `## 变更日志` **追加**一行（不修改历史行）；同步 `Docs/CHANGELOG.md`（[`DocSpec.md`](DocSpec.md) §4）。
- 设计结论被推翻时，**保留旧结论并标 `⚠ 已作废`**，写明作废原因与替代方案；不要静默删除（历史事故的追溯价值高于整洁度）。

## 11. 提交前自检清单

- [ ] 文件名符合 `…Design.md`，位于 `Docs/Design/`
- [ ] 标题为中文且以「设计」结尾，未重复文件名
- [ ] 元信息 6 行齐全，`状态` 取值合法，`最后更新` 与 `变更日志` 末行一致
- [ ] `## 变更日志` 为 4 列表格，历史行未被改写
- [ ] `## 1. 目标与边界` 含目标表格与「不在范围内」
- [ ] 一级章节数在 8–12 个之间，编号从 0 起连续、无跳号
- [ ] 每个枚举关系用表格，每个非显然选择有「为什么」
- [ ] 所有表格列数一致，单元格内竖线已转义或改为代码块
- [ ] 代码块均标注语言；ASCII 图可正常对齐（等宽字符，不用中文全角符号画框）
- [ ] 「实现现状」用 `✅` / `⛔` 标注，未实现项写明目标版本
- [ ] `## 相关文档` 链接均为有效相对路径
- [ ] 数字类结论带来源与日期
- [ ] UTF-8 无 BOM、LF 换行、无行尾空格
- [ ] 已同步 `Docs/CHANGELOG.md`（需求驱动时同 `Docs/RequirementList.md`）

## 12. 常见反例

| 反例 | 问题 | 改法 |
|---|---|---|
| 「本系统采用了先进的分层架构，极大提升了可维护性」 | 营销词 + 无信息量 | 「分三层：契约层/内核层/接入层；改动接入层不影响内核」 |
| 「导出模块负责导出」「上传模块负责上传」 | 同义反复，读者学不到东西 | 写输入、处理、输出、失败后果四要素 |
| 通篇 3000 字无表格 | 枚举关系被写成散文，难以核对 | 把「触发方式/阈值/状态」全部表格化 |
| 表格里写 `a\|b` 与非表格行混排 | 列数不一致，渲染错位 | 统一转义为 `a\|b`，或把原始串放代码块 |
| 「已支持对象存储」但代码里只有接口 | 计划当现状 | 移到实现现状表标 `⛔ 二期` |
| 改了设计但没动变更日志 | 读者无法判断文档新旧 | 追加变更日志行 + 更新 `最后更新` |
