# Docs/Proposal — 需求提案目录

> 用途：存放**面向决策的需求提案（Proposal）**——在动手改代码或改数据之前，把"要解决什么问题、现状是什么、打算怎么做、需要谁拍板"写清楚。
> 本目录的文档**不是实现规范**，未获批准前不代表任何已生效的约定。

## 1. 什么文档放这里

| 放这里 | 不放这里 |
|--------|----------|
| 需求提案、方案选型、跨环境与跨模块治理建议 | 已批准并落地的实现方案（放 `Docs/Design/`） |
| 需要用户拍板的决策点清单 | 具体改造步骤与验收报告（放 `Docs/Refactor/`） |
| 现状核对数据与差异分析 | 开发规范（放 `Docs/DevSpec/`） |

一句话判定：**文档里还有"待确认决策点"就放这里；决策点清零、开始动手就迁出或归档。**

## 2. 命名规则

格式：**`yyyyMM-NNNN-大驼峰标题.md`**

| 段 | 规则 |
|----|------|
| `yyyyMM` | 提案创建年月，四位年 + 两位月，如 `202611` |
| `NNNN` | **本目录内**四位顺序号，从 `0001` 起，只增不减 |
| `大驼峰标题` | 英文大驼峰（PascalCase），能说明提案主题，如 `DataBaselineSyncProposal` |

示例：

```
Docs/Proposal/202611-0001-DataBaselineSyncProposal.md
Docs/Proposal/202611-0002-BrsRemoteCleanupPolicy.md
Docs/Proposal/202612-0003-CdeuUscAliasRule.md
```

规则要点：

- 编号**在本目录内独立计数**，与 `Docs/Refactor/`、`Docs/Design/` 等其他目录的编号互不干扰。
- 编号**只增不减、不得重号、不得复用**（即使原文档被删除或改名）。
- 新增前先核对已用编号，以下命令应输出空：

  ```bash
  ls Docs/Proposal/ | grep -E '^[0-9]{6}-[0-9]{4}-' | cut -d- -f2 | sort | uniq -d
  ```

- 文档被否决或作废时**保留文件**，在文首状态栏写 `已否决` / `已作废`，不删不改名。

## 3. 文档必备结构

每份 Proposal 至少包含以下小节（顺序可调，内容必须有）：

| 小节 | 必填内容 |
|------|----------|
| 状态栏 | 文首引用块：`状态`（取值为待评审、已批准、已否决、已作废）、依据数据、关联需求编号 |
| 问题陈述 | 要解决的问题，用可核对的事实描述，不写愿景 |
| 现状核对 | 实测数据、代码/库现状，能贴数字就贴数字 |
| 目标与非目标 | 明确"不做什么"，防止范围蔓延 |
| 方案与阶段 | 分阶段动作与产出物 |
| 验收标准 | 每条都可执行核对（命令或 SQL），不写"基本可用" |
| 待确认决策点 | 编号列出，每条给出选项与建议，等用户拍板 |
| 风险与红线 | 涉及删数据/改结构的，必须引用 `Docs/DevSpec/DbSchemaSpec.md` §0 |

## 4. 与其他文档的关系

| 文档 | 关系 |
|------|------|
| `Docs/RequirementList.md` | 提案**批准并落地后**才登记正式需求编号；提案本身不占需求号 |
| `Docs/CHANGELOG.md` | 提案新增/批准/作废时按 `DocSpec.md` §4 记一条变更 |
| `Docs/Design/` | 提案批准 → 实现方案落 `Design/`，本目录文档保留作为决策依据 |
| `Docs/Refactor/` | 动手改造的执行步骤与验收报告落 `Refactor/` |
